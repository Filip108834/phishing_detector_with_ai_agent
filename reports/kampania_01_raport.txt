2. ŚRODOWISKO LABORATORYJNE - ARCHITEKTURA
================================================================================

Usługi (Docker Compose):

  +---------------------+  +---------------------+  +---------------------+
  |     MailHog         |  |      Gophish         |  |    PostgreSQL 16     |
  |  SMTP:  :1025       |  |  Admin:   :3333       |  |  phishing_lab DB    |
  |  Web UI: :8025      |  |  Phishing: :8080      |  |  user: thesis       |
  |  (sieć: lab_inter.) |  |  (sieć: lab_inter.)   |  |  (sieć: db_inter.)  |
  +---------------------+  +---------------------+  +---------------------+
           ^                         |                        ^
           |   SMTP delivery         | API                    |
           |   (port 1025)           v                        |
  +-------------------------------------------------------------------+
  |                      AI Agent (FastAPI)                           |
  |  Host: :8000   Sieci: lab_internal + db_internal + host_access    |
  |  Model: heuristic  DB: PostgreSQL  Poller: MailHog auto           |
  +-------------------------------------------------------------------+

Sieci Docker:
  - lab_internal:  internal: true  (izolowana - MailHog, Gophish, AI Agent)
  - db_internal:   internal: true  (izolowana - PostgreSQL, AI Agent)
  - host_access:   internal: false (mostek do hosta - umożliwia port-binding)

Porty dostępne z hosta (localhost):
  - localhost:8000  ->  AI Agent REST API
  - localhost:8025  ->  MailHog Web UI
  - localhost:3333  ->  Gophish Admin Panel
  - localhost:8080  ->  Gophish Phishing Server

Schemat przepływu e-maila:
  campaign_generator.py
       -> Gophish API (tworzy kampanię)
       -> Gophish wysyła SMTP -> MailHog:1025
       -> MailHog przechowuje wiadomości
       -> campaign_generator eksportuje .eml -> data/raw/<kampania>/
       -> POST /ingest/campaign/<kampania> -> AI Agent klasyfikuje
       -> Wyniki zapisywane w PostgreSQL
       -> GET /results/stats -> raport

4. WYKRYTE BŁĘDY I ZASTOSOWANE POPRAWKI
================================================================================

BŁĄD 1 - Brak pliku .env uniemożliwia start Docker Compose
------------------------------------------------------------
  Objaw:
    docker compose up -d
    -> Error: env file .env not found

  Przyczyna:
    docker-compose.yml zawiera dyrektywę "env_file: - .env", ale plik .env
    nie był commitowany do repozytorium (poprawna praktyka bezpieczeństwa).

  Naprawa:
    Utworzono .env na podstawie .env.example z uzupełnionymi domyślnymi
    wartościami. Klucz Gophish uzupełniony po pierwszym starcie.


BŁĄD 2 - ModuleNotFoundError: No module named 'psycopg2' (kontener Linux)
--------------------------------------------------------------------------
  Objaw:
    docker compose logs ai-agent
    -> ModuleNotFoundError: No module named 'psycopg2'
    -> Kontener w pętli restartowania (Restarting)

  Przyczyna:
    requirements.txt instaluje psycopg3 (psycopg[binary]) na Linuksie,
    ale docker-compose.yml używał dialektu SQLAlchemy "psycopg2":
      DATABASE_URL=postgresql+psycopg2://thesis:thesis@db:5432/phishing_lab

    Dialekt "psycopg2" wymaga biblioteki psycopg2, której nie ma w obrazie.
    Dialekt "psycopg" (bez cyfry) obsługuje psycopg3.

  Naprawa:
    Zmieniono dialekt w docker-compose.yml i .env:
      DATABASE_URL=postgresql+psycopg://thesis:thesis@db:5432/phishing_lab


BŁĄD 3 - Port-binding nie działa (sieci internal: true)
---------------------------------------------------------
  Objaw:
    curl http://localhost:8000/health -> Connection refused

    docker inspect ai_agent --format '{{json .NetworkSettings.Ports}}'
    -> {"8000/tcp":[]}   (pusta lista - brak bindingu)

  Przyczyna:
    Obie sieci Docker (lab_internal i db_internal) mają ustawione
    "internal: true". Sieć wewnętrzna blokuje komunikację z hostem,
    w tym mapowanie portów, nawet gdy kontener deklaruje "ports:".

  Naprawa:
    Dodano trzecią sieć "host_access" (bez internal: true) i podpięto
    do niej mailhog, gophish i ai-agent:

      networks:
        host_access:
          driver: bridge
        # (brak internal: true)

    Kontenery dołączające do host_access zachowują też izolację
    lab_internal/db_internal między sobą.


BŁĄD 4 - Gophish API: "No email template specified"
-----------------------------------------------------
  Objaw:
    RuntimeError: Gophish API error: No email template specified
    (przy próbie tworzenia kampanii)

  Przyczyna:
    Gophish API v1.0 wymaga w payloaddzie kampanii obiektów z polem "name",
    a nie "id":
      Błędny payload:   {"template": {"id": 1}}
      Poprawny payload: {"template": {"name": "lab_phish_bank_alert"}}

    Analogicznie dla pól: "page", "smtp", "groups".
    Kod w simulation/gophish_client.py.create_campaign() używał ID.

  Naprawa:
    a) Zmieniono dataclass Campaign: pola template_id/page_id/smtp_id/group_ids
       zastąpione przez template_name/page_name/smtp_name/group_names (str).

    b) Zmieniono payload w create_campaign():
       Przed: {"template": {"id": campaign.template_id}}
       Po:    {"template": {"name": campaign.template_name}}

    c) Zaktualizowano wywołanie Campaign(...) w campaign_generator.py,
       aby przekazywać nazwy zamiast ID.

    d) Przed ponownym uruchomieniem usunięto zasoby z nieudanej próby:
       curl -X DELETE "http://localhost:3333/api/templates/1?api_key=<KLUCZ>"
       curl -X DELETE "http://localhost:3333/api/pages/1?api_key=<KLUCZ>"
       curl -X DELETE "http://localhost:3333/api/smtp/1?api_key=<KLUCZ>"
       curl -X DELETE "http://localhost:3333/api/groups/1?api_key=<KLUCZ>"


BŁĄD 5 - UnicodeEncodeError przy wypisywaniu znaku "->" na Windows
------------------------------------------------------------------
  Objaw:
    UnicodeEncodeError: 'charmap' codec can't encode character '\u2192'
    (strzałka Unicode -> w komunikacie "Wyeksportowano X wiadomości -> dir/")

  Przyczyna:
    Powłoka Windows (Git Bash / cmd) używa kodowania cp1250, które nie
    zawiera znaku U+2192 (RIGHTWARDS ARROW). Python 3.10 na Windows
    nie ustawia automatycznie UTF-8 dla stdout.

  Skutek:
    Skrypt crash-uje po udanym eksporcie EML, przed zapisem metadata.json.
    Dane są zapisane poprawnie, tylko metadane trzeba było dopisać ręcznie.

  Naprawa:
    a) Zastąpiono "->" przez "->" w campaign_generator.py (replace_all).
    b) Ustawiono zmienną środowiskową PYTHONIOENCODING=utf-8 przy wywołaniu.
    c) Ręcznie zapisano metadata.json dla campaign_bank_alert.


BŁĄD 6 - Brak montowania wolumenu data/ w kontenerze ai-agent
--------------------------------------------------------------
  Objaw:
    curl -X POST http://localhost:8000/ingest/campaign/campaign_bank_alert
    -> {"detail":"Katalog kampanii nie istnieje: data/raw/campaign_bank_alert"}

  Przyczyna:
    Pliki .eml były eksportowane na hosta do katalogu data/raw/, ale
    kontener ai-agent nie miał dostępu do tego katalogu (brak volume mount).

  Naprawa:
    Dodano volume mount w docker-compose.yml:
      volumes:
        - ./data:/app/data

    Po czym restart kontenera:
      docker compose up -d ai-agent

5.4 MACIERZ POMYŁEK (dla e-maili z ground truth = phishing/legit)
-------------------------------------------------------------------

                    Predykcja PHISHING  |  Predykcja LEGIT
  Ground PHISHING:         0 (TP=0)    |        15 (FN=15)
  Ground LEGIT:            0 (FP=0)    |        10 (TN=10)

  True  Positive Rate (Recall):  TP / (TP+FN) =   0/15  =  0.00  (0%)
  True  Negative Rate:           TN / (TN+FP) =  10/10  =  1.00 (100%)
  False Positive Rate:           FP / (FP+TN) =   0/10  =  0.00  (0%)
  False Negative Rate:           FN / (FN+TP) =  15/15  =  1.00 (100%)
  Precision:                     TP / (TP+FP) =  N/A (brak TP)
  Accuracy:                      (TP+TN)/(all) =  10/25  =  0.40 (40%)

  Interpretacja: Model heurystyczny osiąga idealny TNR (brak fałszywych
  alarmów dla legalnych e-maili) kosztem zerowego TPR (wszystkie ataki
  phishingowe zostają niezauważone).

6. ANALIZA SZCZEGÓŁOWA - DLACZEGO HEURYSTYKA ZAWODZI
================================================================================

FORMUŁA MODELU HEURYSTYCZNEGO (agent/ml/heuristic.py):
  score = min(1.0,
      0.15                         # base score
    + 0.05 * keyword_hits          # ang. słowa kluczowe phishingowe
    + 0.15 * urgency_exclamation   # wykrzykniki / "URGENT" / "ACTION"
    + 0.10 * reply_mismatch        # Reply-To != From
    + 0.10 * freemail_sender       # gmail.com / yahoo.com / hotmail.com
    + 0.25 * suspicious_urls       # IP-URL / podejrzane TLD / redirect
  )

  Próg klasyfikacji: score >= 0.50 -> "phishing", score < 0.50 -> "legit"

ANALIZA SKŁADOWYCH DLA KAMPANII PHISHINGOWYCH:
  -----------------------------------------------

  1. KEYWORD HITS - wynik: 0/1 (tylko password_reset dostał 1 hit)
     Problem: Słownik angielski - "verify", "account", "suspended",
     "click", "confirm", "login", "password". Szablony napisane są
     po POLSKU. Odpowiedniki: "zweryfikuj", "konto", "zablokowano",
     "kliknij", "potwierdź" - nie są w słowniku.
     Skutek: 0.05 × 0 = 0.00 dla bank_alert i package_delivery.

  2. URGENCY EXCLAMATION - wynik: 1 tylko dla bank_alert
     bank_alert subject:    "PILNE: Zablokowano Twoje konto bankowe"
       -> wykryto wielkie litery + dwukropek -> +0.15
     password_reset subject: "Twoje hasło wygasło - wymagana zmiana"
       -> brak wykrzyknika ani CAPS -> +0.00
     package_delivery subject: "Nie mogliśmy dostarczyć Twojej paczki"
       -> brak wykrzyknika -> +0.00

  3. REPLY-TO MISMATCH - wynik: 0
     Gophish ustawia From: security-alert@lab.local i brak Reply-To.
     Brak niezgodności -> +0.00.

  4. FREEMAIL SENDER - wynik: 0
     Nadawca: security-alert@lab.local (domena wewnętrzna).
     Nie jest to gmail.com / yahoo.com -> +0.00.

  5. SUSPICIOUS URLS - wynik: 0 (KLUCZOWY PROBLEM)
     Gophish generuje linki w formacie: http://gophish:8080?rid=<id>
     URL analyzer sprawdza:
       a) IP-based URL: "gophish" to nazwa hosta, nie IP -> brak wykrycia
       b) Suspicious TLD: .local / brak TLD -> nie należy do listy .xyz/.tk/.ml
       c) Phishing keywords in URL: "gophish" nie zawiera "login/verify/account"
       d) @ in URL: brak
       e) Redirect params: brak
     Skutek: 0.25 × 0 = 0.00

  Kampania               | base | kw | urg | repl | free | url | SUMA
  -----------------------|------|----|-----|------|------|-----|------

================================================================================
7. WNIOSKI DO PRACY DYPLOMOWEJ
================================================================================

WNIOSEK 1 - OGRANICZENIA MODELU HEURYSTYCZNEGO
   Model heurystyczny oparty na angielskim słowniku słów kluczowych
   i analizie URL-ów pod kątem podejrzanych TLD jest niewystarczający
   do wykrywania polskojęzycznych kampanii phishingowych wykorzystujących
   wewnętrzne domeny laboratoryjne. Osiąga 0% skuteczności (TPR) przy
   100% specyficzności (TNR). Jest to akceptowalny punkt wyjścia, który
   motywuje konieczność zastosowania uczenia maszynowego.

WNIOSEK 2 - WARTOŚĆ ARCHITEKTURALNA SYSTEMU DWUTOROWEGO
   Architektura "heurystyczny fallback + model ML" jest właściwa:
   - Heurystyki działają szybko i nie generują fałszywych alarmów (FPR=0)
   - ML może nauczyć się wzorców polskojęzycznych bez ręcznego rozszerzania
     słownika
   - System zachowuje możliwość działania bez wytrenowanego modelu (graceful
     degradation), co zostało zweryfikowane w tym eksperymencie

WNIOSEK 3 - KONIECZNOŚĆ WIELOJĘZYCZNEGO ZBIORU TRENINGOWEGO
   Zebrane dane kampanii (15 phishingowych + 10 legalnych e-maili po polsku)
   nadają się jako punkt startowy do budowy zbioru treningowego modelu ML.
   Do uzyskania istotnych statystycznie wyników konieczne jest co najmniej
   kilkaset przykładów z każdej klasy.

WNIOSEK 4 - PROBLEM "DOMAIN SHIFT" W SYMULACJACH
   URL-e generowane przez Gophish (http://gophish:8080?rid=xxx) nie
   odpowiadają URL-om rzeczywistego phishingu (np. http://bank-secure.xyz/
   login.php?token=...). Symulacja laboratoryjna wprowadza "domain shift",
   który zaniża wykrywalność URL-ową. Zbiory treningowe powinny zawierać
   rzeczywiste próbki phishingu (np. ze zbiorów PhishTank, OpenPhish).

WNIOSEK 5 - ZNACZENIE NAGŁÓWKÓW E-MAIL
   Analiza nagłówków (X-Mailer: gophish, brak DKIM, brak SPF pass) mogłaby
   jednoznacznie wskazać phishing bez analizy treści. Rozszerzenie modelu
   heurystycznego o reguły nagłówkowe byłoby prostą, wysokoefektywną
   poprawą. W modelu ML nagłówki mogą być osobnymi cechami liczbowymi
   (feat_spf_pass, feat_dkim_present itp.).

WNIOSEK 6 - ŚRODOWISKO DOCKER SPEŁNIA WYMAGANIA IZOLACJI
   Sieć internal: true skutecznie izoluje komponenty laboratoryjne od sieci
   zewnętrznej. Jednocześnie dodatkowa sieć mostkowa (host_access) umożliwia
   dostęp z hosta do UI i API narzędzi. Architektura sieciowa jest poprawna
   i nadaje się do opisu w dokumentacji środowiska badawczego.

WNIOSEK 7 - POWTARZALNOŚĆ EKSPERYMENTU
   Dzięki Docker Compose i skryptowi campaign_generator.py eksperyment
   jest w pełni powtarzalny. Wystarczy usunąć wolumeny (docker compose
   down -v) i powtórzyć kroki 1-9. Metadane kampanii (metadata.json)
   i pliki .eml pozwalają na odtworzenie dokładnych warunków eksperymentu.
